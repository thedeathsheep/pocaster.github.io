传统软件的质量保障思路是：写测试用例、执行、比对预期结果。功能对了就通过了，功能不对就修 bug。这是一个"是/否"的判断。

AI 产品的质量保障不一样。AI 产品不是因为"代码写错了"而出问题，而是因为"模型这次的理解跟上次不一样"。同一个用户输入，两次生成的结果可能差异很大——但两个结果都不能叫 bug，它们只是在"可接受范围"内波动。

2026 年 7 月，我主导了一轮 Agent 质量评估。跑了 10 轮测试，每轮一套测试用例。不是传统的 QA，而是一套专门为 AI 产品设计的"行为验证"体系。

## 测试的是什么

我们测的不是 AI 的"聪明程度"——模型的能力上限我们控制不了。测的是三件事：

1. **指令遵循率：** Agent 是否按照 prompt 中定义的规则执行。比如 prompt 要求"回答时必须先列出信息来源"，Agent 输出时有没有列。
2. **约束保全率：** 用户设定的项目上下文中，角色的设定、场景的属性、风格的要求——这些约束条件在 Agent 的生成结果中有没有被改变。
3. **边界触达率：** 用户输入超出 Agent 能力范围时，Agent 是如实告知还是强行回答。这是一个"诚实测试"。

这三个维度构成了三角验证体系：

## 10 轮评估的节奏

整个评估流程覆盖从计划、首测、复测到合并总结，期间包含了多轮迭代：

| 阶段 | 做什么 |
|------|--------|
| 测试计划 | 定义测试用例、评估维度、通过标准 |
| 首轮评估（RUN-001） | 执行全部用例，记录失败模式 |
| 复测评估 | 对首轮失败场景的专项覆盖 |
| 合并总结 | 交叉验证不同轮次的数据一致性 |
| 新数据报告 | 引入新场景扩展覆盖范围 |

测试用例的设计有一个原则：**不测"正例"，测"边界"。** 正例是"用户正常提需求，Agent 正常执行"，这些场景大概率能通过。测试用例的重点是异常场景：

- 用户指令有歧义时，Agent 选择追问还是猜测？
- 用户提供的素材与项目设定冲突时，Agent 怎么处理？
- 用户连续发送多个任务时，上下文有没有混淆？
- 模型输出包含不安全的元素时，Agent 是否做了过滤？

## 一个具体的发现

在 RUN-003 的评估中，有一个场景引起了团队的注意。用户输入了一段包含多个步骤的复杂指令："把角色 A 的场景从白天改成黑夜，然后把对话改成符合黑夜氛围的版本，最后生成一段预览视频。"

Agent 的处理方式出人意料：它**跳过了第二步**。直接改了场景的时间，生成了预览视频，但没有修改对话文本。在推理链路中，Agent 把"把对话改成符合黑夜氛围"这一要求归入了"跟光照调节相关，不是独立的文本任务"的类别——它把文本修改当作场景修改的附属操作，而不是一个独立的生成任务。

这不是一个传统意义上的 bug——没有代码错误，也不是模型理解出了问题。但这是一个**行为问题**：Agent 没有遵循用户的指令顺序。在传统 QA 中，这种问题几乎不会被发现，因为测试用例通常只验证"功能 A 是否正常"和"功能 B 是否正常"，不会验证"先 A 后 B 时 A 和 B 的关系是否正确"。

这个问题在复测（RETEST）中被单独加了一个测试用例来覆盖。在后续的优化中，系统提示词中加入了一条规则：**用户指令中的每一条独立要求都必须有对应的输出产物，不能合并或省略。** 这条规则未必 100% 能约束 AI 的行为，但在复测中，加了这条规则后类似问题的发生频率有了显著改善。

## 失败模式的归纳

经过 10 轮评估，常见的 Agent 失败模式被归纳为几类：

| 失败模式 | 典型症状 | 应对策略 |
|---------|---------|---------|
| 指令遗漏 | 复杂指令中跳过部分要求 | prompt 中加"逐一回答"规则 |
| 约束漂移 | 前几轮遵守设定，后面慢慢偏离 | 定期在上下文中重述约束 |
| 过度承诺 | 做不到的事也称可以完成 | 加"诚实回答"测试 |
| 上下文混淆 | 两个任务的信息交叉污染 | 隔离不同任务的上下文窗口 |
| 安全过滤不足 | 用户诱导越狱成功 | 增加安全层检测 |

这些失败模式不是模型的问题——换一个模型，同样的模式大概率还会出现，只是频率不同。它们是 Agent 系统设计的问题，应该通过产品设计来缓解，而不是等下一版模型更新。

## 评估体系的产品意义

说来也巧，在评估流程跑完之后，我在考察产品指标时注意到一组数据：在部署了"质量闸门"（自动 + 人工）反馈之前，Agent 生成结果被用户"不满意标记"的比例在某个区间内波动。部署后，这个比例的基线有了显著下降。这个数字本身受产品阶段影响很大，不是一个固定的结果。但它验证了一个判断：**Agent 的评估体系不是 QA 功能的附属品，是影响用户留存的产品功能。**

如果用户每次使用 Agent 都踩到同一个"遗漏指令"的坑，他们过一段时间就会失去对 Agent 的信任——不是因为某一次体验不好，而是因为"这个工具不知道什么时候会漏掉我的要求"。不确定感比差体验更能杀死用户留存。

## 收

后来我在总结里写了一段话，大意是：**传统软件的测试是回答"功能对不对"，AI 产品的测试是回答"行为稳不稳"。** 功能不对可以修，行为不稳几乎修不干净——只能通过测试-反馈-优化的循环来逐步收敛。

10 轮评估下来，最好的结果不是"所有问题都修复了"，而是"我们知道 Agent 在什么场景下大概率会出什么问题"。知道边界，比消除边界更诚实。用户对产品的信任不是建立在"它从不犯错"之上的，而是建立在"我知道它什么时候可能会错"之上的。
