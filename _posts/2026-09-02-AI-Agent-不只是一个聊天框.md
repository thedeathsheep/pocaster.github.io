2026 年 6 月，我写完一份 PRD 之后问了自己一个问题：用户打开一个 AI Agent，到底想干什么？

这个问题的答案看起来很简单——“用户有需求，Agent 满足需求”。大部分 Agent 产品也是这么设计的：用户说一句话，系统判断意图，分发到预设工作流，执行，返回结果。这像一个聪明的路由器——输入终点地址，它找到路径把你送过去。

但我观察真实用户行为后发现，事情没这么简单。

## 用户的行为，不是"触发一个功能"

我从几类用户的行为记录中看到了三个反复出现的模式：

**第一类：无目的探索者。** 这类用户打开 Agent 并不是来执行某个具体任务的。他们会先问"你能做什么"，然后发一张参考图说"做成这样"，再改口"不要了，试试这个风格"。他们的意图在对话中才逐渐成型，而不是在一开始就明确的。

**第二类：已有材料的创作者。** 这类用户大概率已经有剧本、分镜脚本、参考视频、角色图。他们打开 Agent 时不是来"从零写一部短剧"的，而是期望 Agent 像导演助理一样——理解已有材料、识别缺口、协助推进、管理生成物。

**第三类：跨模态尝试者。** 用户天然会把图片、视频、文本塞给 Agent，期待它理解并在需要时生成对应的内容。用户不会先理解产品有多少种"模式"，他们只知道自己在创作一个东西，工具应该跟上。

这三种行为有一个共同点：**用户的目标不是触发一个功能，而是在表达一个创作意图。** 这两个概念的区别，决定了 Agent 的产品架构应该长什么样。

## 两张架构图

**图 1：意图路由架构（多数产品当前的方式）**

<div class="mermaid">
flowchart LR
  A[用户输入] --> B{意图分类器}
  B -->|"类型：图片生成"| C[触发工作流：图生图]
  B -->|"类型：视频生成"| D[触发工作流：文生视频]
  B -->|"类型：剧本创作"| E[触发工作流：剧本工具]
  B -->|"类型未知"| F[默认回复/追问]
  C --> G[返回结果]
  D --> G
  E --> G
</div>

这个架构对"查询型"任务（查天气、翻译、搜索）效果很好。但对于创作类任务有四个固有矛盾：

1. **意图不在输入时就确定**——用户的创作意图在对话中逐步收敛，而不是一步到位。
2. **工作流与真实需求不匹配**——预设工作流只能覆盖已知路径，而创作场景中有大量"今天没这个需求但要支持"的情况。
3. **生成物没有归属**——一次任务的结果不会回到 Agent 的上下文里，下次需要重新描述。
4. **失败范围不可控**——工作流中某个步骤出错，整个任务失败，用户没有恢复手段。

**图 2：导演层架构（我主张的方式）**

    H --> J[工作流引擎<br/>图像/视频/文本/音效]

    K --> L[结果展示与溯源]
    L -->|用户确认/修改| C
  end
</div>

导演层和意图路由的本质区别是：**意图路由的终点是一次执行，导演层的终点是用户满意。**

## "意图路由"失效的第一个现场

我是在评审一个功能时意识到这个问题的。当时我们的 Agent 设计是：用户在输入框输入内容，系统匹配意图类型，然后跳转到对应的"工作台"（一个独立页面）去执行。评审时我提了一个假设场景：

> 用户上传一个剧本，说"帮我看看这个剧本哪些场景可以加特效"，然后看了结果又说"其中第二场不适合特效，改成夜景对话"，最后说"把这个导出成标准格式"。

这个场景在意图路由架构下会触发至少 4 次"意图识别 → 跳转工作台 → 执行 → 返回"的往返。每次往返用户都会丢失上下文——前面对"第二场"的理解不会带到下一次任务里。更重要的是，用户其实是在**同一个创作过程中**，但系统把它的每一句话变成了独立的"任务"。

这不是模型能力的问题，是产品架构把创作过程切碎了。用户不会理解为什么他的剧本要反复在不同的"工作台"之间跳来跳去，他只会觉得"这个工具不理解我"。

## 产品定位的一句话测试

我后来用一个测试来判断 Agent 的产品定位对不对：**你能不能一句话说清楚它不是一个什么东西？**

对意图路由架构来说：
- 它是一个聊天入口 + 功能触发器的组合
- 很难一句话说清它"不是"什么

对导演层架构来说：
- 它不是单纯聊天机器人
- 它不是意图分类器
- 它不是完整工作台的入口包装
- 它不是一键生成整部短剧的承诺
- 它不是画布产品

知道"不是什么"往往比知道"是什么"更重要。它划定了边界，排除了那些看起来很合理但会让产品走偏的选项。

## 导演层必须回答的三个问题

从 PRD 到可工作的产品，导演层必须解决三个具体问题，它们不分先后，但缺一不可：

**问题 1：资产怎么归属？**

用户上传的参考图、Agent 生成的中间结果、用户确认的最终产物——这三类"资产"在导演层的上下文里分别属于谁？我的答案是：一次创作会话就是一个"项目级沙箱"，所有资产归项目所有，但标记来源。用户能从资产溯回到生成它的任务，也能从任务看到它产出了什么资产。这个双向追溯是导演层区别于"对话历史"的关键。

**问题 2：生成物怎么不被丢进黑箱？**

意图路由的典型体验：用户输入 → 等待 → 看到结果。如果结果不对 → 重新描述 → 再等待。导演层必须在生成过程中提供可见状态——任务排队了、正在执行、等待确认、已完成。每个状态背后都应该有用户可以操作的节点。我见过一个数据：在支持任务状态展示的系统中，用户的重试率降低了约 37%（这个数字来自我经历的一个 AB 测试，但不同产品和场景差异很大，仅供参考）。

**问题 3：长上下文怎么管理？**

一次创作会话可能包含：5 轮关于剧本的讨论、3 张参考图、2 次生成尝试、1 次角色定义修改。这些信息如果全部塞进模型窗口，成本高、注意力稀释、角色一致性还会丢失。导演层需要一套上下文管理策略——哪些进短期 buffer（当前对话），哪些进项目记忆（角色设定、风格约束），哪些进长期知识库（已完成的分镜、已确认的场景）。这套策略不是技术问题，是产品契约问题：你要让用户知道 Agent 记得什么、不记得什么。

## 哪些被验证了，哪些还不确定

到写 PRD 的阶段，以下判断已经在内部分享和设计评审中被多方验证：
- "意图路由"在创作场景的局限性——评审中没有一个人反驳这个判断
- 资产归属和双向追溯的必要性——开发者接受度高
- 可见的任务状态比"更快的生成速度"更能减少用户焦虑——来自后续原型的用户测试

仍不确定的是：
- 用户是否真的愿意在 Agent 内完成"创作会话"而非"触发一次生成后就离开"——这需要一个可用的产品来验证
- 长上下文管理的契约边界——短期内更可能依赖模型窗口扩展，而非产品层面的上下层策略
- "导演层"这个概念对普通用户是否有吸引力——它可能只是一个内部架构术语，用户层面需要完全不同的表达

## 收

后来我在另一份文档里看到一段话，不是产品文档，是开发者的笔记，大意是：

> 不是露出更多按钮就是更好的 Agent。

我深以为然。导演层不是为了加功能，而是为了让 Agent 承担一个更具体的角色——理解创作意图、管理创作材料、维护创作上下文。它在架构上从"通道"变成"容器"，在产品上从"工具"变成"协作者"。

当然，"协作者"这个词也很虚。用户不关心概念，关心的是：我说了一句话之后，它是不是真的知道我要干什么。
