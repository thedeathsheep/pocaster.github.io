我手头有一份正在生产环境里运行的提示词文档。导出日期标注得很清楚：2026-07-15。文档开头有一个版本说明和引用路径——

> "当前生产路径：`story_chapters` / 章节正文生成 V2"
> "静态模板来源：`step5_content_template_lean.go`"
> "调用组装来源：`handler_chapter.go`、`story_chapters.go`"

看到这些路径就能感受到：这不是一段"写给 AI 看的文字"，这是一段**有版本号、有调用链、有条件分支的可执行代码**。

## 提示词的"代码结构"

一个生产级的提示词，远比大多数开发者想象的更有结构。拿这份章节生成提示词来说，它的组成是：

```
1. 动态项目 system prompt（角色设定：专业短剧编剧）
2. 项目补充设定前缀（世界观 + 风格 + 场景约束）
3. 渲染后的用户模板（Step5ContentTemplateLean）
4. 质量闸门重写时追加的反馈后缀
```

每一部分都有明确的职责，不分次序：

**System prompt 不是固定的。** 它根据项目状态动态组装——如果项目有名，就插入项目标题；如果有题材，就插入题材短语；如果两个都为空，就用默认值。这是一个控制流：`if projectTitle != "" then insertTitle else useDefault`。

**项目设定前缀有字数上限。** "世界观，最多 1200 个字符"——这是一个人为设定的约束。因为经过测试，1200 字以内的世界观提示既能提供足够上下文，又不会挤占模型窗口。超过这个长度的设定就进入了边际递减区域。

**用户模板是核心逻辑。** 它定义了"生成什么"和"不要生成什么"：剧本层只负责剧情事实和题材主戏点，不替分镜层预埋技术参数。这其实是一组在 AI 语境下定义的"面向对象设计原则"——剧本类只暴露剧情方法，不暴露镜头属性。

**质量闸门是一个可选的后处理步骤。** 如果模型输出不够好，系统可以追加反馈后缀让模型重新生成——不是人工审查，而是一个"自动 + 人工"的混合闭环。

## 提示词有条件分支

文档里有一段让我觉得特别有意思的"题材表达映射"规则。它不是简单的"如果题材是 X，就写 Y"，而是一套完整的**条件 - 动作 - 验证**逻辑：

```
题材不是标签，必须落成剧情事实。
每场先判断 1～2 个主戏点。
按"题材功能 → 可拍承载物/动作 → 可见变化 → 新状态或新压力"写入动作。
不得为了题材氛围新增大纲外能力、敌人、案件、关系、道具。
```

这不是一段"让 AI 自由发挥"的文字。这是一个**生产规则**：定义输入（题材）、约束处理逻辑（必须落成剧情事实）、规范输出（必须有可拍承载物/可见变化/新状态）、限定边界（不得新增大纲外内容）。

写这段规则的过程跟写代码差异不大——明确输入、定义逻辑、规范输出、划定边界。只不过"代码"要求精确，而提示词要求约束下的创造性。

## 可保留的状态要写清楚

文档里有一组"因果可读性"规则特别说明问题了。原文：

> "剧本层必须让观众只看画面和听对白也能复述因果：谁在什么空间、被什么压力推动、想去哪里、通过哪个入口/载具/通道行动、行动造成什么结果、结果如何变成下一场的新状态。"

这其实是在定义一个**数据契约**：每个场景必须输出指定字段。如果场景不满足字段要求（比如缺少"入口/载具/通道"），它在后续的分镜生成环节就会断裂——分镜 Agent 不知道角色怎么从一个空间移动到另一个空间的。

这种"上下游契约"在传统软件开发中是通过接口定义来保证的。在 AI 生成场景中，通过提示词来保证。提示词在这里承担了"接口文档"的角色——不是代码，胜似代码。

## 有一个重要原则不能省略

在章节生成提示词中，有一个"不得"比所有"应"更重要：

> "不得改变既有剧情因果、角色动机和既有角色/场景资产设定。"

这是系统 prompt 的一部分，位于最顶部。它的优先级高于一切"生成好剧本"的指令。它规定了 Agent 可以在什么范围内发挥——可以发挥语言表达，不能发挥剧情因果。这是一个"不变约束"的定义——无论模型多强，不能碰的部分就是不能碰。

这跟代码里的权限检查非常像：你可以调用大部分 API，但写操作需要特定权限。在提示词里，这个权限检查就是"不得改变既有剧情因果"。不是因为技术做不到，是因为改坏了用户没地方修。

## 提示词的单元测试在哪里

传统代码有单元测试，提示词有隐性的"质量门"。这个质量门没有写在代码里，但写在了提示词规则中：

> "质量自检：指出是否存在机械镜头、无动机高级镜头、空间连续性问题或过度炫技。"

这是个有意思的设计——它让 AI 在输出完成后自己检查一遍自己的输出。这不是一个强制阻断（如果自检发现问题，系统未必阻止），但它让 AI 在输出时多了一层自我审查。在一次 AB 对比中，带自检指令的提示词生成的脚本在"术语堆砌"方面的评分比不带自检的提示词生成的脚本有明显的质量差异——不是模型变了，是模型在输出前多了一个"再检查一下"的步骤。

这个"自检"的设计，是从软件开发中的静态代码分析得到的启发。代码在提交前跑一遍 lint 检查，提示词在输出前跑一遍自检——逻辑是一样的，只是机制不同。

## 收

后来我回顾这份生产提示词的设计历程时发现：它经过了一个从"一段优美的文字"到"一段可执行的规则"的转变。最初版的提示词更接近一个"好编剧应该怎么写"的写作指导。生产版的提示词变成了一套"这句话要满足这些条件、不能走哪条路、输出后要自检哪些问题"的规则系统。

写提示词的本质是在写一种没有类型系统的程序。没有 IDE，没有编译器，没有类型检查。一句写错的规则不会在保存时报错，只会在用户看到离谱的生成结果时才被定位。

所以我现在看一份提示词文档，先看它的"不得"列表有多长。"不得"越多，说明这个 prompt 的成熟度越高。不是因为它限制了 AI，是因为写它的人知道边界在哪里。
