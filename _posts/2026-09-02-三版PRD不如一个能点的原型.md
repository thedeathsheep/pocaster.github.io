两年前我喜欢写详细的 PRD。每一条需求都写清楚背景、规则、边界、异常处理。写完之后觉得自己把所有问题都想到了。

但事实是，几乎每次评审都会有人问出让我无法当场回答的问题——"这个状态之后用户还能不能走别的路径？""如果 A 和 B 同时发生怎么办？"

后来我开始在写 PRD 的过程中做一个能点的原型。不是 UI 高保真那种，有时候只是一个带点击流程的线框图，有时是一个把主流程和分支流程串起来的脚本。效果比我想象的好得多。

## 一个具体的例子

有一个后台功能，核心流程是：渠道商提交客户信息 → 后台审核 → 签约 → 返点结算。

我把这个流程写了 14 页 PRD。规则覆盖了：每个状态的审核权限、各状态之间的流转条件、超时未处理的通知机制、异常状态的处置方式。

第一次评审，需求方提了一个问题：如果渠道商提交客户信息后，在"待审核"期间客户自己联系了公司并直接签约，这个状态下系统应该怎么处理？渠道商的信息还会进入签约流程吗？新的签约记录会不会和正在审核的渠道商记录冲突？

这个问题我在 PRD 里没有覆盖到。不是因为粗心，而是因为**文字稿让我线性地思考流程**——我沿着"提交→审核→签约"的主路径写完了，但并行输入的情况在文字稿里很难被系统性地检查。

## 问题不是"遗漏"，是文字有结构盲区

写 PRD 这件事有一个固有缺陷，跟写的人水平无关：**文字是一种线性表达，而产品流程是非线性的。**

一个标准的处理流程如果画成图，通常是这样的：

<div class="mermaid">

  A[渠道商提交] --> B{审核状态}
  B -->|通过| C[进入签约流程]
  B -->|驳回| D[退回修改]
  B -->|补充材料| E[等待上传]
  C --> F{客户方状态}
  F -->|"未自行签约"| G[公司签约]
  F -->|"已自行签约"| H[冲突解决]
</div>

图中加号表示的两个状态——"客户已自行签约"和"冲突解决"——在文字 PRD 里可能出现在"异常处理"章节的一个子条目里。但在图上，它和主流程的关系是**可见的**：它处于"签约流程"的一个分支决策点，而不是一个遥远的异常列表。

我在早期的人生经验中收集过一个对比数据（来自之前的项目复盘）：同等复杂度的需求，用纯 PRD 评审，被发现的流程缺失平均为 4.7 个/次；用原型 + PRD 一起评审，这个数字降到了 1.2 个/次。当然这个数字受产品复杂度影响很大，但趋势是稳定的。

## 模拟运行脚本

后来我做了一个更极端的尝试：把流程写成可运行脚本。不是画原型，而是用代码把"用户点击 A → 系统进入 B → 如果条件 C 则触发 D"的逻辑串起来运行。

这个脚本的执行结果让我发现了三件事：

**1. 状态缺失**
有一个规则写的是"审核通过后自动进入签约流程，签约完成后系统计算返点"。脚本跑了一遍之后发现在我定义的"审核通过"和"签约完成"之间缺少了一个中间状态：审核通过后，系统需要等待渠道商确认是否接受合同条款，不接受的话应该退回修改而不是直接进入签约。这个中间状态在文字 PRD 里被我忽略掉了——因为从产品逻辑上讲，"审核通过"和"进入签约"似乎是原子操作，但实际上它们是两步。

**2. 分支还原**
返点结算的部分，PRD 写了"如果返点比例变动，按公告日期分段计算"。这个规则在文字里看起来很清楚。但脚本执行到这一行时，开发者问了一个还原性问题：分段计算的起止时间点在数据里怎么确定？是以渠道签约时间为准，还是以客户回款时间为准，还是以结算操作时间为准？不同的选择会得出不同的计算结果。PRD 里没有定义这个时间锚点，因为我在写的时候默认"分段计算"已经足够精确了。

**3. 条件冲突**
脚本检测到一个分支冲突：用户通道和系统自动流程可能同时触发同一个状态的变更。例如：渠道商提交材料 → 系统初审自动通过 → 同时渠道商手动撤回。两个操作在同一个时间点到达，系统应该怎么确定最终状态？这个冲突在 PRD 里完全没有覆盖——我假设了"自动审核"和"手动操作"不会同时发生。但现实中这种事情就会发生。

## 三个省时间的发现

做完这个实验后我归纳了三个规律，后续一直用它们指导自己在哪类需求上做原型、哪类需求直接写文档就够了：

**应该做原型的场景：**
- 流程有分支和循环（后台审核、结算、审批流）
- 状态超过 5 个（一个简单的 CRUD 不需要原型，7 个状态以上的流程需要）
- 存在外部系统的"输入"（用户、第三方、自动定时任务都可能触发状态变更）

**可以直接写文档的场景：**
- 纯内容展示类需求（首页改版、列表页优化）
- 策略调整类需求（排名规则变更、权益配比调整）
- 工具链优化（开发工具、测试流程）

这个分类不是绝对的，但它帮我省了不少时间。做过原型的功能，在评审阶段的"意料之外的问题"数量明显更少。

## 原型不是设计的终点

我把"先做原型"变成习惯之后，也发现了一个反作用：有时候原型做得好，会给人"这个功能已经完成"的错觉。评审者看到一个可点击的流程，会倾向于关注交互细节而非逻辑完整性——"这个按钮放左边还是右边"比"这个状态下用户能不能这么做"更容易吸引注意力。

所以我现在的方式是：**先做逻辑原型（线框或脚本），逻辑确认后再做交互高保真。** 两个原型的间距至少有一天，用来冷静地确认："我们刚才确认的逻辑没有因为交互设计而被带偏？"

## 收

我后来回头看那三版招商后台的 PRD，第一版写得最认真、最长，但问题也最多。第二版做了模拟流转，发现了 3 个状态缺失。第三版加了主次流程模拟，终于把评审阶段的问题控制在了可预见的范围内。

如果让我重新排那三周的工作，我应该把第一版 PRD 的时间砍一半，提前一周做一个能点的东西。文字写不清楚的事情，一个可点击的流程让所有人同时看到同一个问题，远比写到第 14 页某个角落里等待被发现可靠。
