通用 AI Agent 有一个尴尬的地方：你对它说"帮我写一段分镜脚本"，它确实能写。但如果你每天都要写分镜脚本，你就会发现它每次的写法都不一样——有时分镜很细，有时就是一句话带过。输出不稳定不是因为模型换了，是因为 Agent 没有固定的"工作方式"。

Agent Skill 的设计试图解决这个问题。它不是一个"更好的 prompt"，而是一个**可复用的执行说明包装**。

## Skill 不是什么

第一版设计草案中，关于"Agent Skill 是什么"的讨论占了很大篇幅，但最有用的结论是确定了"它不是什么"：

- **它不是预设提示词。** 预设提示词是"填入输入框的一段文本"，而 Skill 是一组包含名称、介绍、执行说明和配套参考文档的结构化包。
- **它不是工作流。** 工作流定义了"执行步骤的顺序和条件"，但 Skill 只定义"应该怎么执行"，不规定步骤。
- **它不是技能市场。** 本期的重点是个人可用，不是社区分享。

知道"不是什么"之后，Skill 的产品定位就明确了：**一个能让用户自定义 Agent 行为方式的轻量机制，不改动 Agent 的底层逻辑，只约束它的工作风格。**

## 入口与生命周期

设计 Skill 的交互流程时，我在想一个场景：用户如何在对话中"切换"自己的工作方式？

入口方面最终采用了两个途径：

1. 用户在 Agent 输入框的 `+` 菜单选择 Skills，浏览已启用的 Skill 并选择一个。
2. 用户在输入框里输入 `/`，直接搜索已启用的 Skill 名称。

选择后的生命周期是这个功能最核心的设计：

"标签"的设计看似简单，但它包含了一个产品决策：**选择 Skill 后，系统不把完整的执行说明写入用户输入框。** 这意味着用户的输入框保持干净——他们只需要正常说话，Skill 的约束在后台起作用。如果用户想脱离约束，只需要移除标签，对话就恢复为普通模式。

## 内置 vs 个人

Skill 的产品设计中，"内置"和"个人"的区分花了很长时间来确定：

| 维度 | 内置 Skill | 个人 Skill |
|------|-----------|-----------|
| 创建者 | 产品方 | 用户自己 |
| 可编辑 | 只读 | 可编辑、可删除 |
| 自动启用 | 默认参与匹配 | 默认关闭，用户手动打开 |
| 列表标记 | 不显示来源 | 显示"我的" |

这个区分承认了一个事实：**产品预置的专家流程（"分镜增强"、"剧本格式化"）和用户自创的个人习惯（"总是用 Markdown 输出"、"每次回答前先列大纲"）是两种不同的能力，需要不同的管理方式。**

内置 Skill 的"自动匹配"机制是另一个细节：Agent 会根据当前任务的内容，自动判断是否需要启用某个内置 Skill。这解决了"用户不知道应该选什么 Skill"的问题——在常见场景下，Agent 会自动匹配合适的 Skill，用户不需要理解每个 Skill 的差异。

个人 Skill 的"自动匹配开关"默认关闭，是因为用户对自己创建的东西有更强的控制意识——他们不希望预置了一个 Personal Skill 之后，Agent "擅自"启用它。

## 配套文件系统

比较花时间的一个设计是 Skill 的配套文件系统。一个 Skill 可能需要参考文档（"分镜输出的规范格式"）和示例文档（"正确的分镜写法"）。文件系统的设计原则是：

- 只支持 `md`、`txt`、`doc`、`docx` 四种格式——图片、音视频、脚本压缩包都不支持
- `references` 目录放参考资料，Agent 在需要时才读取
- `assets` 目录放模板或示例，Agent 作为输出格式参考
- 上传时遇到不支持的格式，忽略并提示数量，已支持的文档继续保留

这个"严格的文件格式限制"不是一个技术限制。它来自一个产品判断：**如果用户上传了脚本格式的文件，Agent 不知道该怎么处理。而一个不知道该怎么处理的文件，会让用户觉得"我是不是操作错了"。** 与其增加用户的困惑，不如明确告诉用户：这里只接受这四种文件。

## 优先级与冲突

多个约束同时起作用时，Agent 怎么决定听谁的？PRD 里规定了明确的优先级：

> 规则冲突时，依次以平台安全及确认规则、用户当前明确要求、当前 Skill 指令、Agent 默认行为为准。

这个优先级解决了一个具体矛盾：如果 Skill 说"每次都要先用三幕结构分析"，但用户当前说"直接写，不用分析了"，Agent 应该听用户的。用户当前明确要求 > Skill 指令。这个规则把"用户控制权"放在了最高位置。

## 收

Agent Skill 的设计没有解决所有问题。团队共享、版本历史、Skill 市场、多 Skill 编排都放在了后续阶段。但第一期交付了一个清楚的边界：**Skill 不是让 Agent 变聪明的，是让 Agent 按用户想要的方式工作的。**

把专家流程装进一个按钮里，不是在按钮里塞更多的功能，而是让用户用一个简单的选择，让 Agent 切换一种稳定的工作方式。输出的一致性比输出的上限更重要。
